# hp-watch（ハロプロ RSS・アンオフィシャル）

ハロー！プロジェクト（ハロプロ）・JPROOM・アップフロントの公式サイトの情報を、RSS にして配る。公開先は `https://hello-rss.karin-archive.com`（Cloudflare Workers `hello-rss`）。リポジトリは公開（2026-11-24。非公開のままだと、Actions の無料の時間を使い切ったため）。

- **フィード**（`rss.py`）: 公式のお知らせ・スケジュール・ファンクラブ・ハロショを、RSS にする。題名だけ（本文・画像は持たない）
- **選んで作る RSS**（`/custom/`）: 好きな人・グループ・カテゴリ・言葉だけのフィードを、URL で作る
- **手で入れるページ**（`/import`・鍵つき）: 放送の情報（リンク・ゲスト・メモ）を、あとから足す
- **TVer のリンクの自動**（`tver.py`）: 放送後に、TVer のエピソードのリンクを探して足す
- **ポッドキャスト・YouTube のリンクの自動**（`episodes.py`）: 毎週の番組の、公開されたエピソードを探して足す
- **時計**（`watcher/`）: Cloudflare の Cron Trigger が、公式が変わったときだけ、GitHub の作業を呼ぶ

## About（このサイトについて）

ハロー！プロジェクト関係の公式サイトの情報を、RSS リーダーで読めるようにした、非公式のサイトです。公式の情報の**題名とリンクだけ**を配ります（本文・画像は載せません。読むときは、公式のページへ）。

**どういうフィードか**
- **お知らせ**: 公式のお知らせが載った日に、1回だけ配ります。グループ別と全体があります。公式の記事にグループのタグが付いているので、それで分けています。
- **MEDIA（出演）**: テレビ・ラジオ・雑誌・WEB に、新しく載った出演の予定です（だいたい1週間前に載ります）。毎週・毎月の番組は含めません。ラジオには radiko のタイムフリーのリンクが付きます。
- **今日の予定**: その日の予定を、毎朝1本にまとめます。毎週の番組も含めて、全部です。
- **ファンクラブ**: ファンクラブのニュースを、ニュース・イベント・コンサート・グッズなどのタブ別と、グループ別に配ります（Hello! Project オフィシャルファンクラブと、M-line club）。
- **選んで作る RSS**（`/custom/`）: 好きな人・グループ・カテゴリ・言葉だけのフィードを、URL で作れます。ハロショの新着、アメブロ（グループ・メンバーのブログ）、YouTube（公式チャンネル）も、ここで選べます。

**サイトごと**
- **ハロー！プロジェクト**（helloproject.com）: お知らせ・MEDIA・今日の予定。グループ別あり。
- **JPROOM**（jp-r.co.jp）・**アップフロント**（up-front-create.com）: 同じ形で、所属が個人なので、全員まとめて1本です。人ごとに見たいときは、選んで作る RSS で選びます（アップフロントは、ハロプロ関係の人だけ）。
- **ファンクラブ**（upfc.jp）: ニュースをタブ別・グループ別に。
- **ハロショ**（helloshop.info）: 公式の RSS をもとに、題名だけにしたものを、選んで作る RSS で。

**放送のあとに付くリンク**: 放送が終わると、記事の後ろに、見られるリンク（TVer・radiko のタイムフリー・ポッドキャスト・YouTube など）が付くことがあります。毎週の番組には、放送の前から、radiko の生放送や TVer の番組のページが付きます。

構成:

## フィード（`rss.py`）

公式のJSONから RSS を作る。

- お知らせ: `hp/news/{グループ}.xml`・`hp/news/all.xml`、`jproom/news/all.xml`、`upfront/news/all.xml`
  - タイトルは `2026.11.16 [NEWS] 題名`（公式サイトの並びと日付の書き方）
  - 各フィード最新50件。本文は「グループ・種類・日付」の1行と公式へのリンク（タイトルの繰り返しにしない）
  - 記事の時刻は、こちらが初めて見た時刻（JSONには日付しか無いため）。状態は `state/rss_news_*.json`。初回は今ある分を公式の日付の正午のまま入れる（0時ちょうどだと Inoreader で前日の23:59と表示されたため）。公式の日付が7日より前の記事は、初めて見ても公式の日付のまま
  - リンクは JSON の `link`、無ければ `/news/{id}/`
  - 更新は追わない。載った日に1回配信して終わり（公式の UPDATE の印はタイトルに入れず、カテゴリ欄にだけ残す）
- MEDIA: `hp/media/{グループ}.xml`・`hp/media/all.xml`、`jproom/media/all.xml`、`upfront/media/all.xml`
  - スケジュールの TV / RADIO / MAGAZINE / WEB で、新しく載った予定。毎週の番組は出さない
  - 出演は公式のタグどおり（`HELLO! PROJECT`／`BEYOOOOONDS`／`BEYOOOOONDS：平井美葉` など）。今日の予定も同じ
  - 放送日を過ぎてから載ったものは出さない。WEB・雑誌だけ30日以内なら「[掲載済]」で出す
  - ラジオは radiko のタイムフリーのリンク付き（`radiko.py`）。局名から局IDを引き、radiko の週間番組表で開始時刻とタイムフリー可否を確かめる。局名が合わないときは `radiko.py` の `ALIAS` に足す。無料で聴ける範囲（関東・関西・東海・全国、または都道府県）も radiko の都道府県ごとの局一覧から出す
  - 状態は `state/rss_media_*.json`。初回は今日から1週間分を入れて始める
- 今日の予定: `hp/today.xml`、`jproom/today.xml`、`upfront/today.xml`
  - その日の予定を、毎週の番組も含めて全部、時刻順に1記事にまとめる（記事の時刻は朝5時）
  - 同じ番組・同じ時刻・同じ出演者で局だけ違うものは1行にまとめる。ラジオは radiko のタイムフリーのリンク付き
  - 直近7日分を毎回JSONから作り直す（状態は持たない）
- ファンクラブニュース: `fc/{all,news,event,concert,goods,stream,other}.xml`（全体・ニュース・公式のタブ5つ）と `fc/group/{グループ}.xml`（8グループ）。M-line club のファンクラブ（`upfc.jp/m-line`）も同じ作りで、`mline/{all,news,fcevent,ticket,goods,contents,other}.xml`（タブは公式のもの）。29人分の個人別は静的には作らず、選択式で選ぶ。ファンクラブごとの設定は `rss.py` の `FC_SITES`
  - Hello! Project オフィシャルファンクラブ（`upfc.jp/helloproject`）のHTMLを読む（JSONは無い）。「すべて」の一覧（1ページ15件）の1ページ目を見て、新しく載った記事を足す。初回は2ページ分
  - ニュースは、公式のタブには無いが「すべて」の中にある分類。そこだけ別のフィードにしている
  - グループ別・人別は、そのページの一覧（`news_list.php?gid=…`、1ページ目）に載っているかどうかで決める（記事にはグループ・人の印が無い）。番号（gid）はそのページの「view more」のリンクから読んで、状態に持つ。M-line の人の一覧は、ファンクラブのトップのページから毎回読む（読めなければ前回の分）
  - 更新を見分ける印（`Last-Modified` など）が無いので、`rss.yml` が動くたびに見る（ハロプロ・JPROOM の公式の中身が変わったときと、毎朝5:00）
  - 日付は公式の書き方（`2026.11.19`）のまま。記事の時刻は、お知らせと同じ決め方（初めて見た時刻、分・秒は0。初回は日付の正午）
  - 状態は `state/rss_fc.json`（M-line は `rss_fc_mline.json`）。取得に失敗しても、前回の状態があればそれでフィードを書く（他のフィードの公開を止めない）。1グループだけ失敗したときは、そのグループだけ飛ばす
- JPROOM・アップフロント（`up-front-create.com`。同じ仕組み・同じ版。会社全体のサイトで、ハロプロ以外の人も入る）は所属が個人なので、どれも全員まとめて1本。人ごとに見たいときは選択式（下）で選ぶ
- `index.html`（一覧）と `all.opml`（まとめて登録）
- 手元で試す: `python rss.py --out public --state-dir /tmp/rss-state`（`state/` を汚さないように）

- 公開: `.github/workflows/rss.yml` が `rss.py` を動かし、`wrangler.toml` で Cloudflare Workers（`hello-rss`）に送る。呼ばれるのは、公式が変わったとき・毎朝5時・手で入れたとき（下の「動かす仕組み」）
  - GitHub の Secrets に `CLOUDFLARE_API_TOKEN`（テンプレート「Edit Cloudflare Workers」、アカウントと `karin-archive.com` に絞る）と `CLOUDFLARE_ACCOUNT_ID` が要る。無い間は公開を飛ばす
  - どちらかのサイトの取得に失敗した回は公開しない（そのサイトのフィードが消えるので）
- 手で入れた分（`manual/`）は、記事の後ろに足す（下の「放送の情報を手で入れるページ」「TVer のリンクを自動で入れる」）

## 選んで作る RSS（`/custom/`）

好きな人・グループ・カテゴリ・言葉だけのフィードを、各自が選んで作れる。選んだ内容はURLに入るので、保存先（KV など）は要らない。

- 選ぶ画面: `https://hello-rss.karin-archive.com/custom/`（トップの一覧からリンク）
- `site=` の昔の名前（`hp`・`jproom`・`upfront`・`fc`・`mline`）も、今の名前として受け付ける（登録済みのURLが切れないように。`watcher/src/custom.js` の `ALIASES`）。`rss.py` の内部のキー（状態ファイルの名前・静的フィードのフォルダ名）は、昔の名前のまま
- URL: `/custom.xml?site=helloproject&kind=news&who=angerme,juicejuice&cat=EVENT&q=ツアー&x=抽選`
  - `site`（公式のURLの名前: `helloproject`・`jp-r`・`up-front-create`・`upfc-helloproject`・`upfc-m-line`・`helloshop`・`ameblo`・`youtube`。ドメインから `www.` と末尾（`.com` など）を除いたもの。名前は `selectable.py` の `SITE_IDS`）と `kind`（`news`・`schedule`。アメブロは `blog`、YouTube は `video`）は必須。**サイトはまたがない**。**お知らせとスケジュールは別**（1本＝1つのサイト × 片方の種類）。ハロショ・ファンクラブはお知らせ（ニュース）だけ
  - `who`（人・グループ）、`cat`（カテゴリ）は任意。カンマ区切りで複数。同じ項目の中は「どれか」
  - `general`: 特定の人・グループに紐づかない**全体のもの**の扱い。`general=1` は全体のものだけ（`who` とは一緒に使えない）、`general=0` は全体のものを除く（`who=angerme&general=0` で、アンジュルムのタグだけの記事）。無ければ含める。1・0 以外は400。全体のものとは、ハロプロは全グループのタグ（`HELLO! PROJECT`）が付いたものと、どのタグも付いていないもの。JPROOM・アップフロントは誰にも紐づかないもの。ファンクラブはどのグループ・人の一覧にも載っていないもの。ハロショはグループのタグが無いもの（店舗・お知らせなど）
  - `q`（含む言葉）、`x`（含まない言葉）: **題名だけ**が対象（本文は持たない・公開しない）。`q` はスペース区切りで全部を含む、`x` はどれかを含むものを除く。全角・半角・大文字・小文字・異体字（﨑／崎、櫻／桜など）をそろえて探す（`watcher/src/text.js`）。題名の飾り（日付・`[NEWS]`・`[RADIO]`・`[FC限定]` など）は探さない。言葉は5個・60文字まで
  - 上の条件は、全部を満たす記事だけ。空なら全部。最新50件
  - 選べない値は400（誤ったURLを、空のフィードとして登録させない）。データが読めないときは503
- 仕組み: 公開のたびに `rss.py`（`selectable.py`）が `data/{site}-{kind}.json`（人・グループ・カテゴリ・題名付きの記事、最大400件）と `data/options.json`（選べる値）、`custom/index.html` を書く。Worker（`watcher/src/custom.js`）がデータを読んで、条件に合う記事だけを RSS にして返す（`Cache-Control: max-age=600`）。**`data/` は公開されているので、本文など公開したくないものは入れない**
- 人・グループのキーは、公式のプロフィールの `slug`（無い・重複するものは `id{番号}`）。名前が空のプロフィールは選択肢に出さない
- スケジュールの元は「新しく載った出演」（MEDIA のフィードと同じ）。新しく載ったものから溜めるので、使い始めは記事が少なく、日がたつほど増える。人・グループは、記事がまだ無くても選べる
- ハロショ（`helloshop.info`）: 公式が WordPress で RSS（`/feed`）を出している。記事（題名・リンク・公開時刻・カテゴリ）を `state/rss_helloshop.json` に溜める（本文・画像は読まない）。初回は直近30日分（3ページ）、あとは新しい記事だけ。取りに行くときは前回の ETag を付けて、変わっていなければ 304 で済ませる（公式への負担を抑える）。更新は、時計が `/feed` の `Last-Modified` を見て（15分おき）、変わったら `rss.yml` を呼ぶ。タグ・カテゴリの英字のIDは `rss.py` の `SHOP_WHO`・`SHOP_CATS`（公式の `/tag/{ID}/`・`/category/{ID}/`。増えたらそこに足す）
  - 公式のRSSは、ページ（画面）には出ていない。`<head>` に自動検出用の `<link rel="alternate">` があるだけ
  - 見送り: 本文の全文保存（公開してしまう・本文のページを1件ずつ取りに行く負担・検索のノイズ・公式が消した記事が残る）、DVDマガジン（配信）のスケジュール入り、`up-front-promotion.co.jp`
- 方針（2026-11-22）: 対象は、ハロプロ・JPROOM・アップフロント（と、もともとあったハロショ・ファンクラブ・M-line・アメブロ・YouTube）に絞った。田中れいな・鈴木愛理・ジャストプロ・個人の公式サイト（小片リサ・小林梓・夏焼雅）・YU-M Entertainment（辻希美・岸本ゆめの）は、いったん作ったが取り除いた。作り方の記録は git の履歴（PR #20〜#24 の範囲）に残す。yum-e のスケジュールは、取り除いたので未対応のまま
- アップフロント・ハロプロ関係の名簿（`hp_people.txt`）: アップフロントには、ハロプロ以外の人（歌手・俳優など）も所属している。「人」の選択肢は、**名簿の人だけ**に絞る（お知らせ14人・スケジュール21人）。記事のデータは絞らない。名簿に無い人の記事も、「全部」や言葉の検索（`q`）には出る。名簿は、名前だけを1行に1人（異体字・空白・全角半角は区別しない）。増やすときは、このファイルに足す。名簿に無いハロプロ関係の人（例: 後藤夕貴・諸塚香奈実・橋本愛奈）は、足すまで選択肢に出ない
- アメブロ（`site=ameblo&kind=blog`。ハロプロのグループ・メンバーのブログ）: **保存しない**。リーダーが取りに来たときに、Worker（`watcher/src/ameblo.js`）が選んだブログのRSS（`https://rssblog.ameba.jp/{ブログのID}/rss20.xml`。最新30件。`ETag`・`Last-Modified`・カテゴリ（テーマ）は無い）を取りに行き、題名・リンク・公開時刻だけにして返す（本文の抜粋は読まない）。同じRSSは Cloudflare のキャッシュで10分使い回す（何人が使っても、1ブログあたり10分に1回ほど）
  - ブログのIDと、グループ・メンバーとの対応は、公式のプロフィール（`blogSlug`。グループは、そのグループのブログ全部／メンバーは、その人のブログ）から `rss.py` の `ameblo_source` が `options.json` に入れる。手で持つ対応表は無い（7グループ・69人・14ブログ）
  - `who`: グループは、そのグループのブログの記事全部。メンバーは、そのメンバーのブログのうち、**題名にその名前がある記事**（グループのブログは、題名の末尾に書き手の名前を書く書き方が多い。ニックネームだけ・名前を書かない記事は拾えない。絶対ではない）。名前の照合は、全角半角・空白・大文字小文字・異体字（﨑／崎、櫻／桜、澤／沢、嶋／島など。`watcher/src/text.js`）をそろえる。題名の先頭に `[グループ名]` を付ける。`general`（全体のもの）・`cat` は無い（400）
  - **なぜ、ハロプロのブログだけか**: JPROOM・アップフロントは1人に1つのブログなので、ブログ全体＝その人の公式のRSSで足りる（そのURLをトップの一覧に載せている）。ハロプロのグループのブログは、複数のメンバーの記事が混ざっていて、テーマ（カテゴリ）でも分かれていない。人で絞るための仕組みが要るのは、ここだけ。ブログ全体を見たいだけなら、公式のRSSを直接使うほうが確実なので、全体用のフィードは作らない
  - **なぜ、保存しないか**: 更新の印が無く、見張るには全ブログを取りに行くしかない（更新のあるブログ全部で1日に約57記事・RSSの合計1.6MB）。保存する利点（さかのぼれる）より、動かす回数の負担のほうが大きい。リーダーが取りに来る間隔なら、最新30件で足りる（アンジュルムは約5日分）。ハロショは逆で、更新の印（`ETag`・`Last-Modified`）があり、量も少ない（1日1.2件）ので、保存して溜める
  - 一部のブログのRSSが読めなくても、読めたブログの分は返す。全部読めなければ502
- YouTube（`site=youtube&kind=video`。ハロプロ公式のチャンネル19個と、今の事務所に所属している人の個人チャンネル6個）: アメブロと同じく**保存しない**。Worker（`watcher/src/youtube.js`）が、選んだチャンネルの公式のRSS（`https://www.youtube.com/feeds/videos.xml?channel_id=UC…`。最新15件。公式のキャッシュは15分）を取りに行き、題名・リンク・公開時刻だけにして返す（説明は読まない）。同じRSSは Cloudflare のキャッシュで15分使い回す
  - 対象は、公式の一覧（https://helloproject.com/link/）にある17チャンネルと、JPRTube・decarbo46（どっちっちchannel）。`rss.py` の `YT_CHANNELS`。チャンネルのID（`UC…`）は、チャンネルのページの RSS の印から引いて、`state/youtube_channels.json` に残す（引くのは、一覧に足したときの1回だけ）。個人のチャンネルは、今の事務所に所属している人だけ（アップフロントクリエイト・JPROOM・ジャストプロ。高橋愛・鈴木愛理・勝田里奈・宮本佳林・小関舞・藤本美貴。画面では「メンバー・個人」に入る）。卒業生・フリーの人は対象にしていない
  - `cat`: `video`（動画）／`shorts`（Shorts）。リンクが `/shorts/` の形かどうかで見分ける。Shorts は全体の3割ほど
  - `embed=1`（YouTube だけ。ほかは400）: 公式の埋め込みプレーヤー（`youtube-nocookie.com/embed/{動画のID}`）を本文に入れる。動画そのものを持つのではなく、YouTube 公式のプレーヤーを呼ぶだけ。リーダーによっては、記事の中の埋め込みが表示されない（その場合、リンクから開く）。無ければ、これまでどおり題名だけ
  - 公式がRSSを出しているので、チャンネル全体を見たいだけなら、トップの一覧にある公式のRSSをそのまま使うのが確実。動画とShortsを分けたい・複数チャンネルをまとめたい・埋め込みたい、のときにこの画面を使う
  - 一部のチャンネルが読めなくても、読めた分は返す。全部読めなければ502
- 手元の確認: `PUBLIC_DIR=<rss.py の出力先> NODE_USE_ENV_PROXY=1 node watcher/test.mjs`（時計の確認は、公式サイトへ本物の HEAD をする）

## 動かす仕組み（Cloudflare の Cron Trigger が時計、GitHub Actions が作業）

GitHub Actions の定期実行は時刻を当てにできないので使わない。Cloudflare の Worker `hello-rss`（フィードを配る Worker と同じもの）の Cron Trigger が、決まった時刻に GitHub の作業を `workflow_dispatch` で呼ぶ。RSS に関する作業は3つで、それぞれ独立して動く。

| 作業 | ワークフロー | 呼ぶタイミング（Cloudflare の cron は UTC） |
|---|---|---|
| フィードの作成と公開 | `rss.yml` | ハロプロ・JPROOM の公式の中身が変わったとき（15分おきに、公式のJSONの `ETag` を、前回の作り直しのもの（`data/watch.json`）と比べて、違えば）、ハロショの `/feed` が更新されたとき、毎朝 05:00 JST（今日の予定）、手で入れたとき・TVer のリンクが入ったとき |
| TVer のリンク | `tver.yml` | 毎朝 05:00 と 18:00 JST |
| ポッドキャスト・YouTube のリンク | `episodes.yml` | 毎朝 05:00 と 18:00 JST |

- cron は `*/15 * * * *`（公式の更新の検知）・`0 20 * * *`（05:00 JST。`rss.yml`・`tver.yml`・`episodes.yml`）・`0 9 * * *`（18:00 JST。`tver.yml`・`episodes.yml` など）の3つ
- フィードに無いURLは、トップページ（一覧）へ302で移す（`watcher/src/index.js` の `fetch`。あるファイルは Cloudflare が直接返すので、ここには来ない）。Worker が受けるのは、`/custom.xml`（選んで作る RSS）・`/import`（手で入れるページ）と、それ以外の302
- 時計のコードは `watcher/src/index.js`、cron の設定はルートの `wrangler.toml`。RSS の公開（`rss.yml` の `wrangler deploy`）のたびに、フィードと一緒に送り直す。時計の手順を変えたら、次の RSS の公開から効く
- `rss.yml`・`tver.yml`・`episodes.yml` は、`ref: main` で、いまの main から始める（続けて2回呼ばれたとき、後の実行が古い状態から始まって、状態のコミットが衝突するのを防ぐ）
- Worker は記憶（KV など）を持たない。二重に呼んでも、どの作業も新しい分だけを処理するので困らない
- 公式の更新の記録: `rss.yml` が更新のたびに `state/observe.jsonl` へ1行（版の時刻・見つけた新着の件数）。取りに行く時間帯を決めるための記録

## 設定（Secrets）

値は、チャットにも、リポジトリにも書かない。

- **GitHub**（リポジトリの Settings → Secrets and variables → Actions）: `CLOUDFLARE_API_TOKEN`・`CLOUDFLARE_ACCOUNT_ID`
- **Cloudflare**（hello-rss → Settings → Variables and Secrets → Secret）:
  - `GH_TOKEN` … 時計が `rss.yml`・`tver.yml`・`episodes.yml` を呼ぶための fine-grained トークン（このリポジトリだけ・Actions の実行権限だけ。期限が切れると呼べなくなる）
  - `GH_DATA_TOKEN` … 手で入れるページが `manual/import.json` を読み書きするための fine-grained トークン（このリポジトリだけ・Contents の読み書きだけ）
  - `DASHBOARD_KEY` … 手で入れるページの鍵

## 運用メモ

- `rss.yml`・`tver.yml`・`episodes.yml` は、`state/` と `manual/` の自動の分に差分があったときだけコミットする
- 判定方法を変えたら、`state/` の該当のファイルを消して作り直す（消さないと、前の判定が残る）
- `state/` には、取り除いた源（田中れいな・鈴木愛理・ジャストプロ・個人の公式サイト・YU-M）の古い状態ファイル（`rss_news_reina.json`・`rss_airi.json`・`rss_justpro.json`・`rss_ogata.json`・`rss_kobayashi.json`・`rss_miyabi.json`・`rss_yume.json`）が残っている。害は無い
- 手元の確認:
  - `python rss.py --out /tmp/rss-out --state-dir /tmp/rss-state`（全部作る。時間がかかる。`state/` を汚さないように、別の場所に）
  - `PUBLIC_DIR=<rss.py の出力先> NODE_USE_ENV_PROXY=1 node watcher/test.mjs`（Worker。公式サイトへの HEAD は本物、GitHub は偽物）
  - `python3 test_tver.py`（TVer。ブラウザなし）・`python3 test_weekly.py`（毎週の番組の取り出しと、最初から入れておくリンク）・`python3 test_episodes.py`（ポッドキャスト・YouTube）

## 放送の情報を手で入れるページ（`/import`・鍵つき）

- 管理用。入力ページは `watcher/src/import.js`（ページ自体は何も出さない。データを読むのも保存するのも、鍵（`DASHBOARD_KEY`）を入れてから）。読み書きに使うトークン（`GH_DATA_TOKEN`。このリポジトリの contents だけ）と鍵は、Worker の secret に入れる（値はチャットやリポジトリに書かない）
- 項目は、放送日の前後の期限内のものから選ぶ。リンクは何本でも（名前とURL。https のみ）、ゲスト名とメモも入れられる。入れた中身は一覧に出る。保存すると `manual/import.json` に書かれ、`rss.yml` が呼ばれてフィードに反映される
- **毎週・毎月の番組**（MEDIA のフィードには出さない分）も、1回分ずつの項目として出る。一覧には、放送後3日の分を「毎週」の印つきで出し、絞り込みにも「毎週」がある。**「毎週」タブ**は、番組ごとにまとめて、前後の1回分ずつに、リンクが付いているかを出す（✓ 反映済み・… 待ち（今日の放送）・✗ 未反映（放送の翌日を過ぎても無い）・○ これから）。放送の翌日に反映されているかは、ここで見る
- 毎週の番組の、1回分の項目の元は `data/weekly.json`（`rss.py` が毎回書く）。項目の識別（guid）は MEDIA と同じ形（`{サイト}-media-{ハッシュ}`）なので、手で入れた分・自動の分を、同じ仕組みで結べる
- 期限は放送日の3日後まで。`rss.py` の `load_manual` と、保存のときの掃除（`merge`）が、同じ日で切る。期限が切れた分は、フィードにも入力ページにも出ない
- 本文は変えない。記事の後ろに、メモ・ゲスト・リンクを足すだけ（`rss.py` の `apply_manual`）

## 毎週の番組の、最初から入れておくリンク（`manual/programs.json`）

- 毎週の番組には、放送の前から、行き先のリンクを入れておく。放送後に、そのうえで、タイムフリーやエピソードのリンクを足す。`today.xml`（今日の予定）の行と、手で入れるページの「毎週」に出る
- **ラジオ**: radiko の生放送（局ごと。`radiko.live_url`）。自動（記録は要らない）
- **テレビ**: TVer の番組のページ（TVer にある番組だけ）。`tver.py` が、番組が TVer で見つかったときに、`manual/programs.json` に足す
- **Spotify・ポッドキャスト・YouTube**: `manual/sources.json`（手で書く。番組ごとに `spotify`＝Spotify の番組のページ、`podcast`＝公開のRSS、`youtube`・`youtube_channel`＝チャンネル）。番組のページのリンク（Spotify・YouTube）は、放送の前から付く。**Spotify は、ポッドキャスト（RSSから取ったエピソード）とは別の欄・別のリンクの名前**にして、混ぜない（Spotify に公開のRSSが無い番組があるため。公開のRSSが無い番組は `podcast` を書かない）
- `data/sources.json` に、この行き先の一覧を公開する（手で入れるページの「毎週」が使う）
- **線引き**: `sources.json` に入れるのは、公式の予定（スケジュール）に枠がある番組だけ。公式が載せていない番組（ポッドキャストだけの番組など）は、入れない（ポッドキャストにエピソードがあっても、追わない）
- 番組のキーは、`{種類}|{番組名をそろえたもの}`（`rss.py` の `program_key`。全角・半角・記号をそろえる。局名は入れない）

## 公式の更新の見つけ方（`data/watch.json`・ETag）

- ハロプロ・JPROOM の公式は、**15分ごとに必ず作り直される**（版 `versionDir` も、ファイルの `Last-Modified` も毎回変わる）。そのため、「最近作り直されたか」を見ると、毎回「更新あり」になり、`rss.yml` が1日に約100回動いていた（非公開リポジトリの Actions の無料枠を使い切った原因。2026-11-24）
- 公式のJSON（お知らせ・スケジュール）の `ETag` は、**中身のハッシュ**。作り直されても、中身が同じなら変わらない（お知らせのファイルは、14回作り直されても同じだった。スケジュールは、実際に36件が変わったとき、変わった）
- 作り直し（`rss.py`）は、使った公式のJSONの `ETag` を `data/watch.json` に公開する（`hpwatch.ETAGS`）。Worker（`watcher/src/index.js` の `officialChanged`）は、15分おきに、公式の今年のお知らせ・スケジュールの `ETag`（HEAD）を、`data/watch.json` と比べて、**違うときだけ** `rss.yml` を呼ぶ。Worker は何も覚えず、公開したデータが記憶になる
- `data/watch.json` が無い（初回）・片方のサイトの記録が無いときは、1回呼ぶ。今年のJSONが取れないときは、呼ばずにエラーとして記録する
- 見つけられないもの: 記事の削除など、`ETag` が変わらない変更は無い（中身が変われば `ETag` も変わる）。公式が `ETag` を付けなくなったら、`data/watch.json` と必ず違う扱いになり、毎回呼ぶ（その場合は、毎朝5時の実行だけにする）

## 放送後の TVer のリンクを自動で入れる（`tver.py`・`tver.yml`）

- 放送日から3日（手で入れる分と同じ期限）のテレビの予定（新しく載った単発の予定と、**毎週・毎月の番組の1回分**）について、番組名で TVer を検索して、**番組名と放送日が合う**エピソードのリンクを `manual/auto.json` に書く。毎週の番組は、地方局の遅れ放送もあるので、放送日の8日前までのエピソードのうち、いちばん新しいものも使う。見つからなければ何も入れず、期限まで次の実行でまた探す（局名では合わせない。局の書き方が TVer と違うため）
- 検索のページは JavaScript で描かれるので、GitHub Actions の中でブラウザ（Playwright の Chromium）で読む。取るのは、エピソードのURLと、結果の行の番組名・放送局・放送日だけ（説明・画像は取らない）。番組名ごとに1回、1回の実行で最大25回、間は2秒あける。TVer の `robots.txt` は、何も禁止していない（2026-11-24 に確認）
- 動かす時刻: 毎朝 05:00 と 18:00（JST）。Cloudflare の既存の呼び出し（`0 20 * * *` と `0 9 * * *`）に `tver.yml` を足してある（cron の数は増やさない）。変わったら、コミットして `rss.yml` を呼ぶ
- 手で入れた分（`manual/import.json`）が優先。手で入れた分にリンクが無いときだけ、自動のリンクを補う（`rss.py` の `load_manual`）。入力ページの一覧には「自動」と出て、直して保存すれば、手の分が優先される
- 自動で見つからないもの: TVer に無い番組（NHK・CS・地方局の一部など）、まだ載っていない回。ラジオは radiko のリンクが自動で付くので、対象にしない
- 確かめ: `python3 test_tver.py`（ブラウザなし）。本物の検索は `python3 tver.py --list`（探す項目だけ）か、`tver.py`（手元では `TVER_CHROMIUM` に Chromium のパスを入れる）

## ポッドキャスト・YouTube のリンクを自動で入れる（`episodes.py`・`episodes.yml`）

- 対象は、`manual/sources.json` に `podcast`（公開のRSS）か `youtube_channel`（チャンネルのID）がある、毎週の番組。放送日が今日から14日前までの1回分に、公開されたエピソードを結びつけて、`manual/auto_episodes.json` に書く（リンクは放送日から14日まで出す）
- **ポッドキャスト**: 番組のRSSのエピソードの題名に日付があれば（「2026年11月15日放送分」「11/16」など）、放送日と合うものを選ぶ。日付が無ければ、公開日が、放送日の6日前から10日後までの、放送日にいちばん近いもの。題名に別の日付があるものは選ばない。リンクの名前は「ポッドキャスト」
- **YouTube**: チャンネルの公式のRSS（最新15本）から、放送日（日本時間）に公開された動画のうち、題名に番組名があるもの。リンクの名前は「YouTube」
- **Spotify**: RSSが無いので、ここでは探さない。番組のページのリンクだけを、`sources.json` から付ける
- 番組ごとの最新のエピソード（5件）を `manual/episodes.json` に残す。手で入れるページの「毎週」が、翌日までにリンクが反映されたかを、番組ごとに確かめるのに使う
- 動かす時刻: 毎朝 05:00 と 18:00（JST）。Cloudflare の既存の呼び出しに `episodes.yml` を足してある。結びつきが変わったら、コミットして `rss.yml` を呼ぶ
- 手で入れた分が優先。手の分にリンクが無いときだけ、自動のリンクを補う（TVer の分と合わせて、`rss.py` の `load_manual`）
- 確かめ: `python3 test_episodes.py`（ネットワークなし）。本物は `python3 episodes.py --list`
